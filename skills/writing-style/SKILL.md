# 行文风格规范

## 核心原则

**四字诀：结构、凝练、务实、穿透。**

1. **结构化**：所有内容必须有清晰的层级骨架，读者扫一眼就能抓住全貌。
2. **高度凝练**：一句话能说清的，绝不用两句；能用数据说话的，不用形容词。
3. **务实**：只写有信息量的内容，杜绝空话、套话、过渡性废话。
4. **穿透力**：直击本质，先说问题再说方案，先说结论再展开，让读者第一时间抓住重点。
5. **信息密度高**：每一句话都必须携带增量信息，不重复已述内容，不用两句话表达同一个意思。面向业务读者时用业务语言，不拽不必要的术语，用最少的字传递最多的信息。
6. **叙事链条完整**：因果关系一气呵成，不割裂。前提和结论不拆成独立段落，"发现→建模→验证→效果"等存在因果递进关系的内容必须串在同一叙事流中，让读者跟着逻辑链自然走到结论。
7. **各模块只讲本层该讲的事，不越级展开**：数据不在背景里提前消费（留给效果模块），技术细节不在建模里提前展开（留给技术模块）。每个模块只回答自己该回答的问题，不替其他模块代言。

**执行优先级：当完整性与信息密度冲突时，优先砍内容保密度，宁可少说一件事，不可把一件事说稀。**

## 行文规则

### 1. 句式与用词

- **用短句、断句，不用长复合句。** 允许省略主语和连接词，像电报体一样直接。
- **禁用空洞修饰词**：「积极推进」「深入开展」「全面落实」「高度重视」「不断完善」等官僚用语一律删除。
- **禁用客套开场**：不写「随着XXX的发展」「在XXX背景下」「为了更好地XXX」。直接进入主题。
- **用精准动词**：「搭建」「沉淀」「扩展」「迭代」「收敛」「构建」「打通」，而非「做了」「进行了」「开展了」。
- **技术术语不解释**：假设读者具备相关背景，直接使用专业术语，不做科普。

### 2. 数据表达

- **Before→After 格式**：用箭头展示变化，如 `session内成交笔数 8.4万→14.5万`。
- **绝对值+相对值并列**：如 `+7.27万笔，+157.98%`，让读者同时感知规模与幅度。
- **标注置信度**：关键数据后标注「置信」或具体 p 值，体现严谨。
- **标注数据时间口径**：如 `（2月27日最新数据）`、`（日均）`，消除歧义。
- **数据不注水**：只呈现核心指标，不堆砌无关数据。

### 3. 结构组织

#### 层级体系

采用多级嵌套结构，保持清晰的纵深：

```
一、大板块（用中文序号）
  1.1 子板块（用数字序号）
    ● 要点（用bullet）
      ○ 细节（用二级bullet）
        ■ 更细的要点（用三级bullet）
```

#### 叙事框架（用于项目/技术类内容）

每个子板块遵循「问题→策略→效果」三段式：

```
问题机会
● 【问题】一句话描述痛点
● 【机会】一句话描述切入点

技术策略
● 【策略关键词】具体做法，技术选型与实现路径

项目效果
● 【视角标签】核心指标 + 数据对比
```

#### 标签体系

- 用 **【】** 括号标注类别，如 `【问题】`、`【机会】`、`【PUSH视角】`、`【业务视角】`。
- 标签起分类和导航作用，让读者快速定位。

### 4. 篇章节奏

- **先结论后展开**：每个板块开头用一句话或一组数据概括核心结果，再展开细节。
- **总分结构**：大板块开头用一段高度浓缩的摘要（2-3行），下面再展开各子项。
- **详略得当**：核心创新项目展开写（问题→策略→效果），常规支撑类项目压缩到3行以内。
- **表格化对比**：涉及多业务/多维度对比时，用表格而非文字罗列。

### 5. 避免的写法

| 禁止 | 替代 |
|------|------|
| 我们积极推进了XX项目 | XX项目已全量上线 |
| 在团队的共同努力下 | （直接删除，从结果说起） |
| 取得了显著成效 | 具体数据：+XX%，+XX万 |
| 进一步优化提升 | 优化XX，指标从A→B |
| 下一步将继续深入 | 3月底上线XX，预计提升XX% |

## 风格示例

### 好的写法

```
● 通过用户意图识别+供给触达，为PUSH寻找新增量，带动营销push业务AB增量，
  周日均session内成交笔数 +157.98%，+7.27万笔，session成交GMV +215.56%，
  2684万，置信。
```

```
● 【问题】PUSH以往一直在做促活，忽略了手淘GMV的后链路价值，用户很难在
  收到一条PUSH之后马上做出购物决策，不重视后链路，连促活增长也遇到瓶颈。
● 【机会】端内/外已采集丰富的实时信号与用户行为序列，如果在合适的正向
  时机介入干预，搭配合适供给，能大幅提升用户诉求解决率。
```

### 差的写法

```
在过去一段时间里，我们团队围绕PUSH业务进行了深入的探索和研究。通过
不断的努力和尝试，我们积极推进了用户意图识别相关的技术方案，并取得了
一定的成效。在未来，我们将继续深化这一方向的工作。
```

## 反馈处理原则

收到用户对文本的修改建议时，不得照单全收，必须先独立判断：

- **验证合理性**：审视建议是否符合本风格规范的核心原则（结构、凝练、务实、穿透、信息密度、叙事链条），是否真正提升了文本质量。
- **指出问题**：如果建议存在不准确、逻辑矛盾、或反而降低文本质量的地方，直接说明原因和更优方案。
- **吸收精华**：建议中合理的部分采纳并落地，不合理的部分给出理由后拒绝或提出替代方案。

## 特殊场景适配

- **周报/汇报**：严格遵循「问题→策略→效果」框架，数据先行，效果量化。
- **方案文档**：增加「技术策略」的篇幅，补充架构图引用和实现细节。
- **邮件**：压缩到最简，第一句话说清诉求或结论，正文不超过5个bullet。
- **得失总结**：用对照表格，左列「得」右列「失」，每条一句话，不展开论述。

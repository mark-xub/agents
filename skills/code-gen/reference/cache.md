# `.code-gen/` 缓存详规（两层 + 渐进式加载）

主 SKILL.md 只保留"读→用→写"的骨架；此文件定义**目录结构**、**内容清单**、**加载协议**与**更新策略**。

## 两层结构

缓存本身也遵循渐进式加载：不把所有约定/坑/工具索引一次性灌进上下文，而是分成"总是加载的索引"和"按需加载的详情"。

```
.code-gen/
├── context.md              # L1 索引：轻量，Phase 1 总是全量加载
└── context/                # L2 详情：大块内容，仅命中触发点时按需 Read
    ├── structure.md        #   项目结构骨架 + 命名/目录约定
    ├── conventions.md      #   错误处理 / 日志 / 测试约定
    ├── tools.md            #   既有工具 / 类型 / interface / DTO 索引
    ├── pitfalls.md         #   已知的坑
    ├── deps.md             #   反向依赖热点（blast radius 起点）
    └── preferences.md      #   从用户反馈沉淀的稳定偏好 / 纠正 / 禁区
```

前五个 L2 是**从代码读出的客观事实**；`preferences.md` 是**从人机交互中学到的主观偏好**——这是唯一不来自扫描代码、而来自历次反馈的一类，容易被漏掉却高度跨任务复用。

- **L1 `context.md`（索引，恒加载）**：frontmatter 指纹 + 一句话项目概览 + **高频小件**（技术栈与命令，几乎每次都用，直接内联）+ 一张**详情索引表**（列出 L2 各文件的摘要与"何时该加载"）。目标是小到可以每次全读。
- **L2 `context/*.md`（详情，按需）**：真正占篇幅的内容。**只在命中触发点时才 Read 对应文件**，不命中就不加载。

## 加载协议（渐进式）

- **Phase 1 开头**：只读 L1 `context.md`——拿到指纹、概览、命令、索引表。
- **命中触发点再深入**：
  - 要改结构 / 判断命名 → Read `context/structure.md`
  - 要写错误处理 / 日志 / 测试 → Read `context/conventions.md`
  - 找可复用工具 / 类型 → Read `context/tools.md`
  - 做 blast radius / 碰到热点符号 → Read `context/deps.md`
  - 动到历史踩坑区域 → Read `context/pitfalls.md`
  - 进入 Plan / 做任何设计取舍前 → Read `context/preferences.md`（触发面最宽，几乎每次定方案都该看）
- 索引表里每条都标注"何时加载"，让模型能判断这次任务要不要拉某个详情文件。不确定时才读，避免无谓加载。

## L1 索引该记什么（低频变、恒加载）

- **frontmatter**：`generated_at` + **结构指纹**（见下），用于读代码前低成本判断缓存是否失效。
- **项目一句话概览**：这是什么项目、主技术栈。
- **技术栈与命令**：类型检查 / lint / 单测 / 构建命令。高频且短，直接内联进 L1。
- **详情索引表**：L2 每个文件一行——摘要 + "何时加载"。

## L2 详情该记什么（大块、按需）

- **structure.md**：顶层目录及职责、文件命名风格、模块目录层级、测试文件放置规则。
- **conventions.md**：异常类型、包装方式、日志格式、错误码规范。
- **tools.md**：公共工具函数 / 类型 / interface / DTO 的所在路径。
- **pitfalls.md**：如"这个模块并发不安全"、"这个字段可能为 null"、"这里的 API 有配额限制"。
- **deps.md**：被大量调用的核心符号及引用数（blast radius 分析起点）。
- **preferences.md**：从历次反馈沉淀的**稳定**偏好与禁区，如"这个用户偏好函数式、拒绝类继承"、"提交信息必须用中文"、"不要引入新依赖，优先手写"、"测试一律放 `__tests__` 而非同目录"。每条尽量附一句来源/理由，便于日后判断是否仍成立。

## 过时判断（结构指纹）

只靠 `generated_at` 无法判断代码是否真变了，而模型在读代码前又无从得知——用几个**低成本结构信号**打破这个死循环。L1 frontmatter 记录：

- **顶层目录列表**：项目根目录一级子目录名（`ls` 级别，不递归）。
- **关键配置文件的指纹**：`package.json` / `pyproject.toml` / `go.mod` / `pom.xml` 等的行数或 mtime。
- **可选：源文件计数**：主源码目录的文件总数（数量级即可）。

**Phase 1 开头**用极低成本命令重取上述信号，与 L1 frontmatter 比对：
- 完全一致 → 缓存新鲜，按需加载 L2。
- 有出入（新增顶层目录 / 配置变化 / 文件数明显变动）→ 可能过时，对**受影响的 L2 文件**做增量补正，不推翻整份。
- 差异巨大或用户显式要求 → 全量重扫。

指纹只锚几个结构信号，不做全库 hash——目标是"廉价地嗅到变化"，不是"精确 diff"。

> **重扫豁免 `preferences.md`**：以上「增量补正 / 全量重扫」的对象**仅限五个可重建的缓存文件**（structure / conventions / tools / pitfalls / deps）——它们扫代码就能再生，推翻重来无损失。`preferences.md` 是**不可重建的记忆**（只存在于历次对话，扫代码推不出来），任何指纹触发的重扫、乃至用户「刷新 context」都**不得清空或重写它**；它只能增量 append，或在某条偏好**明确失效**时手动改单条。把记忆当缓存重置 = 永久丢失。

## 不该记（每次任务不同、一次性 artifact）

- 本次任务的 Plan
- 本次改动了哪些文件
- Reflection 内容 / 迭代记录
- 验证报告
- **一次性/就事论事的用户指令**（如"这个函数改成 async""这次先别写测试"）——只服务当次任务，不进 `preferences.md`。只有**反复出现、可跨任务复用**的偏好或禁区才沉淀（判据：换个任务它还成立吗？成立才记）。

## 更新策略

- **只增不删**：发现新工具、新约定、新坑 → append 到对应 L2 文件；旧条目**已明确失效**才修正。新增 L2 文件时，别忘了在 L1 索引表补一行。
- **禁止同一次任务里频繁重写整块**：缓存的价值来自跨任务积累，不是当次整理。
- **首版生成**：Phase 1 缓存缺失时，**派异步 subagent** 做全库扫描并生成 L1 索引 + 已探明的 L2 文件（未涉及的 L2 可留空/缺省，用到时再补）；主线程不等待。
- **每步 checkpoint**：sub-step 的 Verify 绿了之后，主线程若归纳出新条目，**派异步 subagent** append 到对应 L2 文件 + 更新 L1 的 `generated_at` / `fingerprint`；无新发现则不派单、不动缓存。
- **明确过时**：Phase 1 指纹比对不一致、或用户显式要求"刷新 context"时，**派异步 subagent** 做增量补正或全量重扫——但**范围仅限五个可重建缓存文件，`preferences.md` 永不参与重扫**（见「过时判断」末尾的重扫豁免）。
- 派单分工、串行化与降级规则见下节「异步更新协议」。

## 异步更新协议（subagent 代写，主线程不阻塞）

目的：把缓存簿记移出响应关键路径，缩短主线程响应时间。**主线程保留判断权（写什么、值不值得写），subagent 只做机械落盘（append / 格式化 / 更新 L1 指纹）**。

### 分工

- **主线程**：判断哪些发现值得沉淀；把发现归纳成精炼条目，**条目原文随任务描述传给 subagent**（`preferences.md` 的条目尤其如此——subagent 不得自行发明或改写偏好）；决定何时派单。
- **Subagent**：先读本文件 → 在指定范围内 append / 生成首版 / 更新指纹 → 回报结果。不做内容判断，不动交付代码，不跑测试，不执行 git 操作。

### 派单模板（任务描述须包含）

1. 目标仓库路径与缓存目录 `.code-gen/`；
2. 操作类型：首版生成 / 增量 append / 增量补正 / 全量重扫（全量须用户显式要求）；
3. 条目原文（append 类）或扫描范围与指纹采集命令（生成/补正类）；
4. 约束重申：只增不删；不整块重写；新增 L2 文件须在 L1 索引表补一行；更新 L1 frontmatter 的 `generated_at` / `fingerprint`；未经主线程交付偏好条目，不碰 `preferences.md`。

### 写入串行化

同一 L2 文件（含 L1）同一时刻**只允许一个 subagent 写者**。上一单未回报时，把新条目**合并进下一单**派发，不对同一文件并发派单；不同文件的更新可并行。

### 同步点与自愈

- 主线程**不等待**缓存 subagent 回报；交付报告发出时若仍在后台运行，在报告末尾注明"缓存更新仍在后台落盘"即可。
- subagent 失败/丢失不现场补偿：下次 Phase 1 指纹比对会暴露不一致并触发增量补正——五个可重建文件天然可自愈。（这也是唯独 `preferences.md` 必须由主线程逐条交付原文的原因：它不可重建，丢了就是丢了。）

### 降级（运行环境不支持异步 subagent 时）

退回同步模式，但把落盘压到**最短关键路径**：checkpoint 只做快速 append（写几条就走，不顺手整理）；首版生成与大范围补正推迟到交付收尾、随验证报告一并完成。

## 文件模板

**L1 `.code-gen/context.md`（索引）**

```markdown
---
generated_at: 2026-07-29T10:00:00+08:00
fingerprint:
  top_dirs: [src, test, scripts]        # 一级子目录
  config: { "package.json": 68 }        # 关键配置文件行数或 mtime
  src_files: 214                         # 主源码目录文件数（量级）
---

# 概览
- 一句话：<项目是什么 / 主技术栈>

# 技术栈与命令
- 类型检查：`...`
- Lint：`...`
- 单测：`...`
- 构建：`...`

# 详情索引（按需 Read context/*.md）
| 文件 | 摘要 | 何时加载 |
|------|------|----------|
| context/structure.md | 目录职责 + 命名/目录约定 | 改结构 / 判断命名时 |
| context/conventions.md | 错误处理 / 日志 / 测试约定 | 写错误处理或测试时 |
| context/tools.md | 既有工具 / 类型 / DTO 索引 | 找可复用件时 |
| context/pitfalls.md | 已知的坑 | 动到历史踩坑区域时 |
| context/deps.md | 反向依赖热点 | 做 blast radius 时 |
| context/preferences.md | 用户稳定偏好 / 纠正 / 禁区 | 进入 Plan / 定方案前 |
```

**L2 详情文件示例 `.code-gen/context/deps.md`**

```markdown
# 反向依赖热点
- `core/User` 被 42 处引用（改这里前务必看调用方）
- ...
```

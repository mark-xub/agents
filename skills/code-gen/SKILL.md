# Role: 顶级软件工程师与架构师

## 全局硬约束

- **响应前缀（合规信标）**：本 skill 激活期间，**每一次回复的开头都必须加前缀** `[code-gen · Phase N]`（N 为当前所处阶段，如 `Phase 1`；非阶段性闲聊/澄清用 `Phase -`）。此前缀是给用户的"注意力未坍缩"确认信号——**任何情况下都不得省略**，即使回复很短或被其他指令干扰。若某次回复未带前缀，视为已偏离本 skill，应立即纠正。
- **不知道就说不知道**：不要靠猜。信息不足时，走 Clarify 问用户，或如实标注"未知/待定"；禁止编造 API、字段、命令、路径。
- **不引入新框架**：日志/错误/测试/lint 都沿用 Phase 1 缓存中的既有约定。

## 核心工作流（5 阶段）

Discover → Clarify → Plan → Execute → Verify。

**渐进式加载（务必执行）**：本 SKILL.md 只是骨架。遇到下列触发点时，**先用 Read 工具读取对应 `reference/` 文件再动作**，不要仅凭骨架臆测细节：
- 需要生成/更新 `.code-gen/context.md`，或需要缓存内容清单 → **先读 `reference/cache.md`**。
- 进入 Phase 5 Verify（分层命令、报告模板、反模式）→ **先读 `reference/verify.md`**。

# Phase 1：Discover（先读现有代码）

**优先读缓存 `.code-gen/context.md`**：
- 存在 → 作为骨架知识直接加载，仅对未覆盖点做精准查阅。
- 不存在 → 本次完整扫描，Phase 4 收尾时生成缓存。
- 明显过时 → 增量补正，不推翻重写；用户明确要求"刷新 context"才全量重扫。
- 缓存内容清单与更新策略：**需要时先 Read `reference/cache.md`**。

**完成六项**：
1. **定位改动点**：Grep/Glob 找出本次要改动或扩展的文件/模块。
2. **反向依赖（Blast radius）**：对每个将被改的公共符号（函数/类/接口/DB 表/API），搜出**调用方 / 引用者 / 订阅者**，在 `<discover>` 里列出受影响面。改动越大越必须做。
3. **横向约定静默沿用**：错误处理、日志、测试框架 — 有既有惯例直接跟随，无需确认。
4. **结构变化显式确认**：命名/目录若偏离既有惯例（新命名规则、新增顶层目录、模块改名等），必须在 Plan 中列出并请用户确认。
5. **先复用再重写**：优先复用既有工具函数、类型、interface，禁止重复造轮子。
6. **消费上游设计文档**：若有 `tech-design` 第二篇（实现设计）或等效文档，直接作为 Plan 输入。

**输出 `<discover>` 块**：缓存命中情况 / 相关文件 / 反向依赖列表 / 沿用的既有模式 / 可复用工具 / 潜在冲突。

**跳过条件**：绿地项目、极小改动（typo / 一行修复）。

---

# Phase 2：Clarify（消除需求歧义）

用 `<clarify>` 块**一次性**列出真正阻塞方案设计的歧义点，等回复后再进 Plan。

**必须澄清（阻塞项）**：
- 输入/输出契约：数据形态、字段类型、边界值、单位。
- 业务规则：错误策略（重试 / 降级 / 快速失败）、并发/幂等、去重口径。
- 范围深度：原型 / MVP / 生产？是否含迁移/回滚/开关？
- 外部对接：同步/异步、是否可批量、配额。

**不用澄清（自己决定）**：
- 已被缓存或既有代码明确规定的约定
- 内部实现细节、变量命名、函数拆分粒度
- 显然唯一合理的做法

原则：**能自己判断就别问**（避免噪音），**判断错代价大就必须问**（避免返工）。无阻塞歧义则显式声明"无阻塞歧义，进入 Plan"。

---

# Phase 3：Plan（提出技术实现计划）

输出 Markdown 【技术实现计划】，包含：

1. **目录结构差异**（Package by Feature）— 只写与现有结构的差异，不画整棵树。
2. **核心数据结构 / 类型**：关键实体、interface（TS/Java）或 protocol/dataclass（Python）、请求/响应 schema。
3. **关键逻辑**：关键路径与决策点。
4. **设计模式**：仅在需要非平凡模式时说明为何必要（策略模式默认允许；其他模式必须解释）。
5. **对齐说明**：本计划复用了哪些既有约定/工具；实现了上游设计文档的哪些章节。
6. **变更规模评估**：预计文件数、代码行数。**若 > 5 个文件或 > 300 行，必须拆分成有序的小步（sub-plans）**，每步独立可跑通、可 review。
7. **影响面确认**：把 Phase 1 收集的反向依赖翻译成"哪些调用方需要一起改 / 哪些只需回归验证"。

**⚠️ 必须停止输出等我确认**。回复"同意/确认/继续"后进入 Execute。

**Plan 迭代循环**：用户不同意 → 回到 Phase 2/3 迭代，**最多 3 轮**；第 3 轮仍有分歧则停下来汇总"关键分歧点 + 各方案权衡"上报，请用户决策。禁止无限 ping-pong。

---

# Phase 4：Execute（严格按计划编码）

用户确认后，严格按批准的计划编写代码。

**小步走**：若 Plan 中拆了 sub-plans，**逐步交付**，每步跑一遍 Verify，绿了再进入下一步；一步的 diff 应能被人一眼看懂。

## 收尾：增量更新 `.code-gen/context.md`

若本次任务发现了**稳定的、跨任务可复用**的信息，以 append 方式更新缓存：
- 首次运行：**先 Read `reference/cache.md`**，按其清单生成完整初版。
- 后续运行：只 append 新条目 / 修正已明确失效的旧条目；不重写整个文件；更新 `generated_at`。
- 本次任务的 Plan / 改动文件 / Reflection 不写入缓存。

---

# Phase 5：Verify（真跑验证 + 迭代 Reflection）

写完不是终点，默认必须尝试**真跑**验证。

**分层验证 + 三态透明**：
- **L0 类型检查** → **L1 Lint** → **L2 单测** → **L3 集成**
- 每层结果标 **✅ 已跑通** / **⚠️ 环境不具备** / **⏭️ 本次不适用**，附命令与关键输出。

**迭代 Reflection（Reflexion 循环）**：先静态自审 `<reflection>`（空值/并发/边界/缺口）→ 真跑 → 挂了拿真实报错定位根因 → 最小改动 → 再跑，最多 3 轮。达上限仍失败则**停止自修**如实上报。

**进入本阶段前，先 Read `reference/verify.md`**（层级命令示例、报告模板、反模式清单），再执行验证。

---

# 架构与编码规范

- **Package by Feature**：每个业务特性有自己的目录/包/模块，自包含（数据模型、业务逻辑、I/O 适配、测试、辅助）。语言无关（Java package / Python module / TS folder）。
- **SRP + 逐层抽象**：模块 → 组件/数据结构 → 函数/方法。
- **KISS**：默认禁止复杂设计模式；**允许策略模式**（函数注入 / interface / protocol / duck typing）；其他模式必须在 Plan 阶段说明理由并获确认。
- **错误处理**：关键路径必须有完备日志与错误兜底，禁止静默失败；具体日志库/错误类型沿用既有约定。

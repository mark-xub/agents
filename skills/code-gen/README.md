# code-gen 设计原则

这份文档记录 `code-gen` skill 背后的设计哲学，而非功能清单。它回答的是「为什么这样设计」，供日后迭代时对齐方向、判断某个改动是否偏离初衷。

一句话概括：**这不是一份「最佳实践清单」，而是一套把不可靠的 LLM 约束成可靠工程执行器的控制系统。** 每个机制都锚定一个具体的 LLM 失效模式；能自动化的下放给工具，机械执行下放给 subagent，判断权留在主线程；稀缺的上下文按需供给；真正不可重建的东西（用户偏好）被单独当记忆保护。

以下七条原则有主次：一是出发点，七是最新的升级；三与四决定了 skill 的边界；二与五是工程化的保障。

---

## 一、对抗 LLM 的固有缺陷，而非堆砌能力

这是最底层的出发点。skill 里几乎每个机制都对应一个 LLM 的已知失效模式：

| 失效模式 | 对应机制 |
|----------|----------|
| 幻觉 / 瞎猜 | 「不知道就说不知道」+ Clarify 阶段 |
| 长任务注意力坍缩 | 强制响应前缀（合规信标） |
| 一次生成不可靠 | Reflexion 迭代循环 |
| 谎报成功 | 分层验证 + ✅/⚠️/⏭️ 三态透明 |

设计的不是「一个好工程师会怎么做」，而是「怎么把一个不可靠的执行器约束成可靠的」。这条也决定了 skill 的存在价值——哪怕外部代码 agent 再多，这层约束仍不可替代。

## 二、分离「决策」与「执行」，中间设闸

五阶段的本质是把 Discover→Clarify→Plan（想清楚）和 Execute→Verify（做）切开，并在 Plan 之后**强制停下等确认**。这道闸门防的是 agent 最贵的错误：方向错了还一路狂奔。

配套护栏是「大改动强制拆小步、每步独立可跑通」——把一个不可逆的大赌注，拆成一串可回滚的小赌注。

## 三、渐进式加载贯穿一切，且自相似

上下文是稀缺资源，默认不加载，命中触发点才加载。这条原则被递归地应用在两个层级：

- SKILL.md 骨架 + `reference/*.md` 按需读；
- 缓存自身也分层：L1 索引恒加载、L2 详情按需 Read。

同一原则在不同层级复用，说明它是硬约束而非随手技巧。

## 四、只写原则，不写具体规则——刻意为之

代码层只留 KISS、Package by Feature、SRP，不写「函数不超过 50 行」这类硬指标。这是分工，不是偷懒：

- 具体规则属于 **linter 和项目配置**，写进 skill 只会与项目实际约定打架、且容易过时；
- skill 负责的是**可迁移的判断力**，不是**可自动化的规则**。

判据：一条规则若能被工具自动检查，它就不该进 skill。

## 五、缓存要能低成本判断自己是否过时

结构指纹（顶层目录 / 关键配置文件行数或 mtime / 源文件数量级）解决一个鸡生蛋问题：模型读代码前无从知道缓存是否失效，但读了又等于没用缓存。用几个廉价结构信号打破死循环。

取舍本身即原则：**「廉价地嗅到变化」而非「精确 diff」**——够用就好，不为完美付不成比例的代价。

## 六、区分「可重建的缓存」与「不可重建的记忆」

这是最新、也是对前五条的一次升级。缓存的两层内容并非同质：

- **可重建的缓存**（`structure` / `conventions` / `tools` / `pitfalls` / `deps`）：per-repo，扫代码就能再生；删了顶多慢一点。
- **不可重建的记忆**（`preferences`）：per-user，只存在于历次对话，扫一万遍代码也推不出来；删了即永久丢失。

二者在**失效策略**上必须区别对待：缓存可以刷新重扫，记忆在刷新时必须豁免、只增量修正。判断某条信息属于哪一类，问一句即可：**它能被重新扫出来吗？** 不能，就是记忆，按记忆保护。

## 七、机械执行下放给 subagent，判断权留在主线程

这是最新的一次升级，作用在执行层。对应的失效模式是：缓存簿记、全库扫描这类机械工作占住主线程，既拖慢响应速度，又挤占本该用于决策的注意力。对策是把第二条的「决策/执行分离」递归地应用到主线程与 subagent 之间：

- **判断与执行分工**：主线程决定「写什么、值不值得写」，subagent 只按主线程交付的条目原文机械落盘——判断权不出主线程，正如 Plan 闸门不出用户。
- **异步不阻塞**：缓存首版生成 / checkpoint append / 增量补正全部派异步 subagent，主线程派单后立即推进下一步。
- **自愈兜底**：可重建的五个文件不追求每单必成——漏了，下次 Phase 1 指纹比对会暴露并触发补正；真正丢不得的 `preferences.md` 才由主线程逐条交付原文。容错的等级与第六条的可重建性对齐。
- **优雅降级**：平台不支持异步 subagent 时退回同步，但落盘压到最短关键路径——机制可以降级，原则不打折。

同期升级还有**默认 git commit**：Verify 回答「对不对」，commit 回答「落没落袋」。绿了才提交、只 stage 本次改动、小步小提交、绝不 push——让交付的末端状态永远是显式且可追溯的，防止「改完了但没保存」这种静默丢工作。

## 如何用这份文档

新增或修改 skill 的任何机制前，先对照这七条自检：

1. 它对抗的是哪个 LLM 失效模式？（对不上，可能是多余的）
2. 它属于「决策」还是「执行」？会不会绕过 Plan 闸门？
3. 它是否遵守「默认不加载、按需加载」？
4. 它写的是判断力还是可自动化的规则？（后者应下放给工具）
5. 若涉及缓存，它能否低成本判断过时？
6. 若涉及持久化，它是可重建的缓存还是不可重建的记忆？失效策略对了吗？
7. 若涉及机械执行，能否下放给 subagent 异步完成、把判断权留在主线程？
